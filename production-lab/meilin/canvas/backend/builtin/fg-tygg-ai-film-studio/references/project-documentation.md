# 项目文档与连续制作

每个故事、广告或系列在用户指定的项目根目录中维护独立项目档案。Skill 安装目录只保存能力规则；不得把项目资料、Blender 文件或用户资产写入其中，也不得扫描未登记的磁盘位置。

## 项目目录前置条件

开始影片项目访谈及创建任何项目文件之前，先明确本次对应的项目根目录；本节也适用于启动问题、文档问答、临时记录和占位文件。

- 用户已给出具体路径、明确选中能唯一对应目录的已有项目，或当前会话已绑定同一项目时，直接复用，不重复询问。
- 用户仅调用Skill，且未指定或绑定项目目录时，按 [首次使用引导](../SKILL.md#首次使用引导) 在最终正文中先展示字符画和简短的作用、合作方式说明，再索取项目保存位置，并给出“当前文件夹新建某项目”或已有路径的表达示例。目录是事实输入，不编A/B/C候选，也不调用系统选择框；不以一句含糊的目录问题或内部规则解释代替使用引导。等待答复期间不创建项目目录或文件，示例目录不代表用户选择；收到的故事想法先留在对话中。
- 当前工作目录、扫描发现的项目、最近修改的项目或包含多个项目的父目录，都不能单独作为用户选定项目根目录的依据。只指定父目录但未明确本次项目时，补问项目名称或具体子目录；用户明确授权助手命名或选择目录的，按其范围执行并说明实际路径。
- 明确目录后，已有项目先读取入口，新项目才创建对应文件夹；首次建立档案时把实际根目录及其用户来源写入项目入口或状态。启动问题和后续产物均保存在该项目内，回复链接指向实际文件。不能先写到工作区根目录，再用“未绑定项目”“启动记录”或“稍后移动”规避归属要求。

正文受限时的文档交互只改变问题交付方式，不改变上述顺序。目录尚未明确时，仍先在聊天中询问目录；明确后才在项目内创建完整问题文档。本节约束影片项目产物；仅维护Skill时，使用已明确的Skill维护目录，不要求另建影片项目。

## 项目上下文门

每次调用先从用户消息寻找 `project_id`、项目名称、显式路径和“继续/下一场/分支”等线索。

1. 用户明确指定现有项目时，先读`PROJECT.md`与`project-state.json`，再沿文档索引读取章节进度、相关Canon和上次交接。入口不存在时，只在该目录用文件名检索已有剧本、分镜、设定、资产清单和交付说明，建立最小索引；不扫描全盘或把该目录当空白项目。
2. 用户说“接着上一场”“沿用人物/地点”且当前会话只有一个已绑定项目时，读取它并先展示继承摘要。
3. 目录归属不明时先按上节询问，不先写范围选择文档。目录明确但本轮创作范围不明时，按 [三选项访谈](interactive-development.md) 从实际可行的继续当前制作、制作已有下一章、续写未写内容、修改/分支或新建中，给三个贴合记录的候选并允许自由描述。不要为了凑选项误称未写剧情已经存在；不要依赖会消失的选项卡。
4. 新建项目时，在用户已明确或授权确定的项目根目录中创建唯一 `project_id` 和对应档案；项目资料不写入 Skill 目录、全局资产库或未选定的工作区目录。

每次加载后先用短摘要说明：这是独立作品还是连续剧情、剧本写到哪里、参考制作/提示词交付做到哪里、实际AI成片做到哪里、会继承的角色/地点/长期偏好及本次范围。新用户要求优先于旧设定；改设定时记录来源与受影响章节，不悄悄覆盖或追改全剧。

## 独立短片、连续剧情与已有剧本

新项目把`project_kind`记为`standalone_short`、`serial_story`或`undecided`；本轮范围另记`work_scope`（章节/场次/剧本段落、任务类型、允许改写范围）。整剧规模、本段时长与生成分段上限相互独立。用户明确只做完整剧本中的第一小节时，先索引全文章节与本次范围，不为未选择的后续章节生成分镜、资产或动画。

用户给定剧本保留原文文件或原始来源，另记`source_script_ref`及章节/段落定位；修改稿与原文分开。`story/sequence-map.md`逐章列出稳定ID、顺序、简短梗概、原文定位、写作状态、参考制作状态、提示词交付状态、AI生成状态和下一任务。创作顺序、故事时序和制作顺序不一致时分别登记，不靠最大章节编号判断全部前文已完成。

| 读取到的事实 | 正确分流 |
|---|---|
| 后续章已有剧本，当前章参考与提示词交付完成 | 若用户要求继续制作，处理已写的下一章；不称为续写，也不擅改原文 |
| 后续章只有梗概/未写 | 若用户要续写，承接Canon与结束状态创作本轮指定部分，同轮交付该部分剧本＋分镜 |
| 当前章尚有已约定产物未完成 | 优先承接该实际阶段，说明具体未完内容；不跳到下一章冒充已交付 |
| 当前章已交付但AI成片未生成 | 如实区分参考交付与最终成片，不自动生成或重复Blender复核 |
| 用户明确指定修改章、下一章或新分支 | 本轮明确指令优先，直接进入相应范围，不重复问“续写还是修改” |

仅当用户只给目录/“继续”且真实范围仍不明时，展示上述事实后用一句普通文字询问“本次希望处理哪一部分？”。例如已读到完整三章剧本、第一章参考交付完成，就回显“第二、三章已有剧本，尚未制作”，不把原文已有内容当作创作空白。

`PROJECT.md` 是一页人读摘要：项目概念、当前剧情位置、锁定事实、当前阶段、正式版本、最近变化和待确认项。`project-state.json` 是机器入口，保存 `project_id`、`approved_revision`、`working_revision`、当前场次、状态、source-of-truth、开放问题、产物状态和上次交接。`memory-index.json` 只索引实体 ID、摘要和关联文件；不要把全部历史全文加载到上下文。

连续剧情的恢复信息必须实际留下：世界观/时间线、人物身份与设定图及代理尺寸版本、创作/剧情偏好、摄影/色彩/声音偏好、章节进度和结束状态。可以合并在已有文档并用`creative_documents`索引，不能因推荐文件名不同而读不到；没有设定的内容明确标未知，不为填空编造世界史。

资产生图阶段另记录 `asset_image_workflow`：`generation_mode`（`user_self_generation` / `assistant_generation` / `mixed`）、`image_directory`、`prompt_package`、当前 `asset_reference_manifest` 和下一待执行图片。逐图输入关系、生成/审核状态及占位记录保存在 manifest，不重复写入所有文档。自行生图先创建同名空白占位并交付一次完整生成卡，语言沿用用户偏好；助手生成直接保存实际成图。目录与占位细则见 [参考图驱动的场景资产](reference-image-driven-assets.md)。继续项目时复用这些路径和进度，不能重建空白占位覆盖成图。

## 记忆分层与状态

`canon/` 仅保存会跨场次继承的事实。创作者偏好默认仅在项目内生效；用户明确要求“以后都这样”后才能创建独立的全局偏好档。`world/character/location` 记录事实，`continuity-ledger` 记录每场结束时角色位置/朝向、道具归属和损坏、关系、时间天气、观众已知信息及下一场必须继承的状态。

剧情偏好记录类型、主题、暴力/情感尺度、叙事视点、节奏倾向、不可改事件及结局方向，并注明项目/章节/镜头适用范围。连续性还区分人物知道什么、观众知道什么、已发生事实和未兑现伏笔；下一章不重复揭示已经知道的信息，不把候选结局当成既定结局。

`screen-language.md` 保存已确认的视觉媒介、摄影视点/景别偏好、构图/轴线、镜头长度策略、手持强度和启用范围、色调/饱和度/反差、光源/质感、声音原则、预演分工与例外。长期偏好和各场具体节奏分开，不把某一场的“快/慢”误写成全项目命令；用户明确选择的整片风格仍须执行。

每个事实、偏好和决定都要标明来源、revision 和状态：`confirmed`（用户确认）、`delegated`（用户授权创作判断）、`proposed`、`inferred`、`superseded` 或 `retconned`。优先级为：本轮用户明确指令 > 当前项目 confirmed 内容 > 用户明确授权的全局偏好 > Skill 默认判断。

沟通方式按 [交互记录同步](interactive-development.md#交互偏好与项目记录同步) 保存于项目文档并由入口索引。默认正文提问；当前正文受限且允许文档交互时，可直接把完整问题与选项交付为文档，正文提供链接让用户查看作答。记录模式、文档路径、链接交付状态和未答题。用户对该方式的授权继续有效，旧会话限制须按当前实际指令重新判断；不因历史记录就永久禁止正文选项。逐题复用已答内容，不把整组“已收到部分回答”当成全部完成。

## 现行事实与历史快照

对影响制作或交付的关键决定，维护当前采用值、来源和适用范围。`project-state.json`指定现行依据，Canon及人读入口与其一致；每份现行文档只保留一套当前摘要，旧决定通过版本链接追溯，不反复叠加多个“现行”段落。历史快照保留创建时事实，不作为相同字段的另一个当前值。仅保留历史文件名时，在现行入口明确其被覆盖字段及新的依据；不能一边链接为“现行剧本”，一边只在新提示词中修正相反事实。

用户新决定形成后，按变更字段同步其使用处：相关设定、镜头/事件、提示词及恢复入口；已归档访谈保留原答复，摘要标清历史状态，避免旧待办重新出现。可在已有文件维护当前覆盖记录，不要求增加固定文件、完整复制历史或改写旧工程。批准状态标明作用的产物与时点，历史“制作中”不覆盖机器入口中对该版本的采用。用户反馈只更新其实际证明的范围；整体效果认可不自动变成各项技术检查通过，用户报告与助手亲见分开记录。

完成交接时，仅凭入口指定的现行材料应能恢复一致的角色、关键动作与结束状态。材料存在差异就先处理有关字段，不凭文件名最新或版本号最大猜测全部内容已采用。动画、外观和提示词版本可独立变化，范围见 [修订交接](revision-and-handoff.md#修订与失效传播)。

## 场次节奏合同

节奏属于 `sequence -> scene -> beat -> shot`，而不是项目级基调。`sequence-map.md` 只说明剧情段落间的能量和信息起伏。每个 `SC_*_scene-plan.md` 必须建立本场独立的 `pacing_profile`，分别描述剧情目的、信息释放、表演能量、相机能量、剪辑密度、声音节律和需要的理解/反应窗口；用叙事原因解释，而非只写数字或“快/慢”。

```yaml
pacing_profile:
  mode: conversational_tension
  information_rate: measured
  performance_energy: restrained
  camera_energy: low
  editorial_density: sparse
  required_readability: [reaction_before_cut]
```

调时分别考虑动作发生、必要的信息读取和结果停留，区分动作完成速度与完成后的余韵。固定总时长下明确新增时间从哪里取得、节省时间用于哪里，不默认把加快动作省出的时间堆入该镜头尾部；整体缩短时先重编事件与镜头，保留必要因果和反应窗口。各阶段可自然交叠，不按固定比例机械拆分。

需要在多个主体或信息间转移注意力时，在现有镜头与声音安排中区分转场耗时、主体可读区间及表达/反应时间；按 [导演节奏](directing-story-and-editing.md#4-节奏层级整场节奏与切点) 记录估时依据和有意交叠。无需新增独立表格或必填Schema字段，认可后的提示词交付不因本条重新计时或返工。

镜头绑定对应 beat，并写明实际帧段、切入/切出理由和 `pacing_intent`。对话可信息紧张但相机克制；动作可角色能量高但保留稳定空间镜头和接触/反应窗口。场次或镜头修改节奏时，同步更新受影响的 beat 时间、ShotSpec、角色及道具事件、Curve 时间映射、相机路径/Marker、附件显隐、结束状态、连续性、轨迹和提示词，不能仅全局加速旧动画。

## 版本、加载与同步

已确认的剧情、人物/世界事实、地点拓扑、镜头表、节奏合同、资产参考图或角色/相机路径改变时，创建新的 `working_revision`，记录变更字段、受影响产物和未变更依据。用户确认后才提升为 `approved_revision`；被替代的旧产物标为 `superseded`，不自动删除。仅修订提示词表达、素材绑定或已知文字错误时，单独记录文本版本及其现行依据，不自动递增动画版本或使已采用工程失效。

持续任务按需读取：续写读项目摘要、前一场连续性和相关人物；改镜头读 `screen-language`、当前 scene plan、storyboard 和 SceneSpec；建场景读地点资料、资产和预算；导出提示词读取当前已确认剧本、分镜、表演/声音设计及用户认可的时间、状态和资产合同，轨迹有则复用。剧本细节须写进实际提示词，不能只根据 Blender 位移数据概括。已知 Blender 手动修改影响提示词时，只同步相关字段；没有已知差异时，不为寻找漂移重开 Blender 或扫描场景。

用户已认可当前模型与动画时，按 [用户确认与视频提示词交付](user-review-and-prompt-handoff.md) 记录用户确认，将当前 revision 提升为 `approved_revision`，阶段转为 `prompt_export`，直接交付。确认本身不递增 revision；技术验证状态单独保留，未验证项不阻挡交付。旧项目无须为此补齐目录、审核报告或新的必填字段。

每次访谈/方案修改、资产采用、静态或动画认可、导出及本段交付时，增量更新入口、章节进度与有关设定；对话即使中断，也能从`last_checkpoint`恢复尚未完成的阶段。结束交付前写明：本段完成范围和真实产物、相关角色/道具结束状态、后续已写未制作的章节、尚未写的部分、下次优先读取哪些文件、已明确的下一动作或待问的范围。这个文档更新不启动Blender、不补审片，也不自动把下一章标为已授权开始。

`segment_complete`、`reference_handoff_complete`和`project_complete`分别使用；只完成本轮片段时不能把整个连续故事标完成。未约定助手执行的上传/AI生成可以列为用户下一步，与尚欠的助手交付分开。

地点和小资产的沉淀、版本和复用规则见 [资产库](asset-library.md)。

## 最小交付记录

建议目录是可选组织方式，不预建空报告；短任务可在已有入口与当前 revision 合并相关记录。**文件拆分可选，已发生的访谈、视觉决定、分镜交付与阶段反馈记录不可省略。** 新的完整视频项目按 [文档模板](production-document-templates.md) 保存并向用户展示：访谈原话与采用值、具名角色、摄影色调、剧本、完整分镜、静态/动画分开的反馈。补充 `generation_profile` 与 `delivery_contract`，定义见 [视频交付](reference-video-delivery.md)。

每轮访谈默认在正文交付问题和三个候选、文档同步记录；正文受限时采用 [文档问题交付](interactive-development.md#会话规则冲突的处理)，完整问题及选项写入文档并给出链接。恢复时区分文档准备、正文展示、授权文档链接交付和已获回答，不把文件存在等同于已阅或问答完成，也不事后补造问答记录。`creative_documents`可引用各文件，`stage_reviews`可记录展示方式、版本、用户原话和范围，具体见 [阶段确认](production-approval-gates.md)。主角用姓名或明确的固定称谓，ID、别名、图片和代理色映射保存在同一人物记录。

人物图与场景/道具同用图片目录和 manifest；`character-bible` 保存角色文字事实，清单保存实际图片与代理/成片身份对应，不把占位视为人物形象。区分 `blender_structure_ready`、`video_appearance_ready`，以及工程、视频、文本、上传绑定和生成结果状态。图不存在时不能把人物提示词当人物图。

补路径、导出进度、上传或认可记录不必递增创作版本。用户改人物外观时，只使相关图片与视频正文/生成结果失效；没有改变代理尺度、动作或结构时，不使 Blender 自动失效。

当前入口只保留一组现行制作指针，分别标明最近采用版本与正在修订/待确认版本。更正状态须替换原先的“等待/已完成”等现行说法，不仅在末尾追加。历史快照记录当时事实及被何版本覆盖；不要求重写历史正文，但它不能继续充当现行输入。事件处置统计从当前事件表派生，变更后同步相关Canon、分镜、说明及提示词。
